# skywave

Listen to shortwave broadcasters and ham radio through public [KiwiSDR](http://kiwisdr.com/public/) receivers, with your own DSP doing the demodulation.

```
browser (Next.js)  ──ws──▶  radio service (Python)  ──ws──▶  public KiwiSDR
  dial, waterfall,           connects to the Kiwi,          raw I/Q, ~12 kHz wide
  audio worklet,             demodulates AM/USB/LSB/CW,
  presets (tRPC + Prisma)    streams audio + spectrum
```

The Kiwi only hands over raw I/Q. Everything from there to your speakers (filtering, sideband selection, envelope detection, AGC, the waterfall FFT) is code in this repo.

## Run it locally

You need Node 24 (see `.nvmrc`), pnpm 12, Python 3.12+, and Postgres (Docker is easiest).

The repo pins pnpm 12.14.0 in `package.json`. If your global pnpm is 10.x, it downloads 12 for you but skips the install script that puts pnpm 12's native binary in place, and every pnpm command then fails with `Failed to switch pnpm to v12.14.0 ... ENOEXEC`. Upgrade the global pnpm first, from outside the repo:

```bash
cd ~ && pnpm self-update 12.14.0
```

If it's already broken, finish the skipped step by hand: `cd ~/Library/pnpm/.tools/pnpm/12.14.0/node_modules/pnpm && node install.js` (the path differs on Linux: `~/.local/share/pnpm/.tools/...`).

```bash
pnpm install
pnpm db:up                                   # Postgres in Docker

cd apps/web
cp .env.example .env
pnpm prisma migrate deploy                   # creates the Preset table
pnpm db:seed                                 # WWV and a few ham/broadcast frequencies
cd ../..

cd apps/radio
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
cp .env.example .env
cd ../..

pnpm dev:radio                               # terminal 1: radio service on :8765
pnpm dev                                     # terminal 2: web app on :3000
```

**Port 5432 already taken** (another project's Postgres)? Put `POSTGRES_PORT=5433` in a root `.env` (see `.env.example`) before `pnpm db:up`, and use the same port in `DATABASE_URL` in `apps/web/.env`.

**Port 3000 already taken** (often another project's Docker container)? Start the web app on another port with `PORT=3001 pnpm dev`, and add that origin (`http://localhost:3001`) to `ALLOWED_ORIGINS` in `apps/radio/.env`; if the radio service runs in Docker, recreate it so it reads the change (`docker compose --profile radio up -d radio`). Don't count on Next.js moving to a free port on its own: when a container holds `127.0.0.1:3000`, `next dev` binds `*:3000` beside it, so `localhost:3000` can reach either app, and the radio service refuses the one it doesn't allow. Docker runs only Postgres and, with the `radio` profile, the radio service; the web app always runs on your machine with `pnpm dev`.

The radio service treats `localhost`, `127.0.0.1` and `[::1]` on the same port as one origin, and the dev server accepts `127.0.0.1`, so `http://127.0.0.1:3000` works too.

Open http://localhost:3000 and press **Listen** with the Receiver field blank: skywave picks the best receiver for you (the same as **Pick best receiver**). Or choose one from the list. WWV on 10,000 kHz AM is the easiest first signal: it's on 24/7 and you'll hear the time ticks.

The list comes from [rx.linkfanel.net](http://rx.linkfanel.net/), which mirrors the [public KiwiSDR list](http://kiwisdr.com/public/) as data (kiwisdr.com itself sits behind a click-through captcha). The web server fetches it at most every 15 minutes and keeps serving the last good copy if the mirror is down, marked stale once it's two hours old. You can always paste an address yourself: a full URL like `http://f4kiy.ddns.net:8073/` is fine (one with no port means 80, or 443 for `https://`), and the port is usually 8073 (a port of 0 or above 65535 is taken as 8073). The list only offers entries on Kiwi ports (80 and 8070–8079, plus 443 for `https://`), so a bad entry can't aim the radio service at some other kind of server; anything you paste yourself can use any port. It also leaves out receivers whose owners only take listeners on the Kiwi's own web page (`ext_api=0`), since those hang up on this app about 10 seconds in.

## Using it

- **First screen:** until the visit's first audio, a line under the header says what skywave is ("Shortwave and ham radio through volunteer receivers around the world.") and what Listen will play: with the dial on 10,000 kHz AM, the default, "Press Listen: the dial is on 10,000 kHz, where the WWV time signal usually is."; anywhere else, "Press Listen to hear this frequency." It shows on every visit, not just the first, and goes once audio arrives (Stop doesn't bring it back).
- **Choosing a receiver:** the header strip says where you're listening ("Listening via Tremolat, France") or, when nothing plays, which receiver Listen will use. **change** opens the receiver drawer under it: the Receiver field, Pick best, the map with the folded IBP beacon and GhostNet strips under it, and the table (it starts shut, even on your first visit, so the dial and Listen are on the first screen; the table inside is already open the first time you open it. It opens by itself when Listen can't pick because the receiver list hasn't loaded, and closes once you choose a receiver, putting focus back on **change**). The Receiver field starts on **Auto (best for this frequency)**: Listen runs Pick best for the dial's frequency. Choosing a receiver yourself (from the table or the map, or by typing an address) pins it: the chip names it, Listen redials it, and it's remembered for your next visit once it has played. The chip's ✕ goes back to Auto without interrupting what's playing. Pick best, or accepting a better receiver, also goes back to Auto; Back doesn't change which you're in. The Receiver and Port fields stay editable while you listen (open **change**): type an address and press Enter or **Switch** to change receivers without stopping (Enter never means Stop). A switch onto a receiver that already has a Skywave listener is refused before anything stops: the station playing keeps going, the dial follows it again, and for a receiver you chose yourself the chip and Receiver field go back to how they were before the switch (the pinned receiver, or blank in Auto, not the address you typed), with the reason in the status line. If you move the dial somewhere the receiver playing can't tune, or at least 1 MHz from where it started with a receiver listed at least 12 dB stronger, skywave asks "Switch to a better receiver?" once the dial has rested for 1.5 seconds. It never switches by itself: **Switch to …** runs Pick best without the receiver playing (so a failure goes back to it), and **Not now** stops it offering that receiver again from this one. Receivers the list doesn't know get no offer, and neither does one another Skywave listener is on (see Receivers), since that switch would be refused. A pinned receiver that turns out to take listeners only on its own web page goes back to Auto. A receiver saved by an older version of skywave isn't pinned; Back offers it instead.
- **Your name on receivers:** the receiver drawer ends with an optional **Your call sign or name** field. Leave it empty and receivers list you under Skywave's own name; fill it in and they list you as "skywave N0CALL", which the receiver's owner and its other listeners can see. The note under the field previews what most receivers will show (many cut names at 16 characters). Letters, digits, spaces and `/ - _`, up to 24 characters; anything else is refused and Skywave's name is used. The name is kept in your browser and applies from your next Listen, even on the receiver already playing; a scan or the wide view uses the same name. The radio service leaves it out of its logs.
- **Receivers:** Pick best tunes the receiver with the highest self-reported HF signal-to-noise ratio that covers your frequency. If it's full, down or otherwise refuses, it tries the next one, up to 3 per click (refusals about the address itself, such as a dead hostname, take no channel on anyone's receiver and don't count, and neither does a receiver that already has a Skywave listener, Skywave's own limit rather than the receiver's; up to 6 receivers in all; a dead name can still take up to 10 seconds to give up on). Receivers that already have a Skywave listener go to the back of the run, and the table marks them "Another Skywave listener is on it": the page asks the radio service's `/held` about the receivers near the top of the list for the dial (about once a minute while the tab is visible, and again when the tab comes back into view or your receiver changes or stops; after a change or Stop it asks once more 5 seconds later, once the service has usually freed the receiver you left, and moving the dial in the meantime doesn't cancel that), and the answer can be that old, so they're tried last rather than skipped. The receiver you're hearing is never pushed back for your own listening. If nothing works, or you press Stop picking, it goes back to whatever you were listening to. A receiver that refused (in a run or when you tuned it yourself) is left out of Pick best for 15 minutes, since the list's copy of it can be that old, unless it plays again. Only a receiver's own answer counts (it's full, takes no apps, or needs a password); a dropped connection, a timeout or an address problem doesn't. Once a receiver plays, Pick best looks done but watches it for 15 seconds more: if it then refuses on its own account (it takes no apps, an owner who changed `ext_api` since the list was fetched; or it says it's full; some receivers do either about 10 seconds in), it moves on to the next one that covers the dial, with a note saying why. Moving the dial doesn't end that watch; choosing another receiver or Stop does. The list's listener counts can be 20 minutes old, so receivers it calls full are ranked last rather than hidden. If the mirror stops answering, the last copy stays in use and the picker says how old it is. If the list never loaded, the picker offers **Try again** (it reads "Trying again…" while a retry you asked for runs) and also asks again on its own every 15 seconds while the tab is visible. Browse the list to search by name, place or antenna, sort by column, and click a receiver to switch to it, even mid-listen. While it's open the list refreshes in the background, but the rows stay put until you sort, filter, search or press **Show all**, or press **Show it** on the "List updated" line between the filters and the table, which also moves keyboard focus to the table. The Night column says whether the sun has set at each receiver right now (sort by it to put the night side first); it's a hint about propagation, not a ranking. After a switch, the **Back to …** button beside the status line names the receiver you heard before and returns to it. It names it by place, the way the header strip does ("Back to Near Tarlee, South Australia"), or by host when the list gives no place or the receiver playing is in that same place; it stays on one line, ending in "…" if it's too long, and screen readers also hear the receiver's full name. If a switch fails or you stop it, Back offers the receiver you were just hearing. Pick best's progress ("… was full; trying …") shows in the status line, which always shows the newest message; where the receiver is shows in the header strip. When a receiver refuses and nothing else is handling it, a **Pick best receiver** link appears beside Back. A connection to the radio service that hasn't opened after 10 seconds is reported as unreachable, and so is a second tune that was waiting on that connection.
- **Map:** the receiver map shows every listed receiver with a known position, shaded where it's night now (lighter for civil twilight) and redrawn each minute. Night dots are brighter, full receivers are rings, and receivers that can't tune the dial's frequency are faint; the one you're hearing is amber, and the one before it has a faint "last" ring. Night is a hint about propagation, not a ranking: Pick best still ranks by signal and load. Click or tap a dot to see the receiver (a crowded spot lists up to 10, with **Zoom into this area** for more), then press **Listen** to switch; a click alone never changes what's playing. The map follows the receiver you're hearing until you pan or zoom, then stays put until **Center** (enabled while you're listening to a receiver with a known position and the map is showing). When playback starts, the listening dot gets one 600 ms emphasis (none under reduced motion). Zoom with ⌘/Ctrl+scroll, two fingers on touch, or the +/− buttons. So the radio starts first, the map loads only after the first audio arrives, or after 5 seconds with nothing playing or connecting. Dots and the greyline draw as soon as the map's style loads; base tiles from [OpenFreeMap](https://openfreemap.org) (no key) fill in after. If the map can't be drawn it shows "Map unavailable" with the reason and offers **Retry map** and **Browse receivers**; the table and Pick best keep working. If the map's code file itself is missing (most likely a deploy replaced it while the page was open), it also offers **Reload page** on a line of its own, which stops the radio; a download that only stalled, or a browser that knows it's offline, gets Retry alone. Reasons: its code didn't load (30 s limit), no WebGL, the browser dropped its graphics context (fails at once; Retry starts clean), the style or the receivers layer didn't draw within 30 s of visible time (a background tab doesn't count), or the base-map tiles aren't loading.
- **IBP beacons:** open **change**, then **IBP beacons** under the map, to unfold the beacon strip. It holds a strip of the five [NCDXF/IARU beacon](https://www.ncdxf.org/beacon/) frequencies (14.100, 18.110, 21.150, 24.930 and 28.200 MHz), the beacon on each one now, and a countdown to the next change; while it's open the map shows all 18 beacons, with the five on the air filled and labeled. The schedule comes from the clock alone (a 3-minute cycle from 00:00:00 UTC, 10 s per beacon per band), using the server's time in milliseconds, which every tRPC reply carries (`x-server-ms`; the Date header is the fallback), so a phone clock a few seconds off still names the right beacon. That time runs on the page's monotonic clock, so setting the computer's clock back doesn't move it. The page measures it every 5 minutes while the tab is visible, when the tab comes back into view, and from any quick reply (a slower one counts when it measures better). A measurement within its own error of the time shown keeps it; a larger difference is a correction, and on an ordinary visit only an error of 1.5 s or more is corrected, so the clock almost never shifts mid-visit. When the computer's clock moves forward by more than 2 s (a sleep, or a change by hand), the page counts from it, asks the server at once (again every 10 seconds until one answers within 5 seconds), and goes back only once the drift is under 1 s, so jitter at the edge can't flap; after a sleep the reply confirms the time, after a change by hand it corrects it. A planned beacon question starts over whenever the time it planned on moves; a question whose timer fired too late for the server to take the answer waits for a later turn, and one left on screen through a sleep closes. Beacon **Listen** while the clock is unsure (no measurement yet, a single slow one, or a jump not yet measured) first checks the time with the server for up to 2 seconds, saying so, then picks the beacon on the air. Over a slow link the clock counts as sure, on its best measurement, once a reply to a later ask comes back. Anything you do meanwhile (choosing a receiver, Pick best, Stop, the dial, the mode, beacon mode, opening or closing the drawer) cancels that Listen. The question gap and the per-channel wait run on the server's clock too. **Listen** on a row tunes that frequency in CW and runs Pick best with receivers ranked for that beacon: listed as free and able to tune the band, 1,000–8,000 km from the beacon (closer is usually inside its skip zone, farther takes three or more hops), and with the path's midpoint in daylight; then by signal as usual. The map draws the great-circle path from that beacon to the receiver playing or being tried. "On air now" is by the clock: the audio runs a second or two behind, and a beacon may be off the air. A beacon NCDXF's [status list](https://www.ncdxf.org/beacon/IBPStatus.csv) has as off the air shows greyed in the strip with "Listed off the air" and NCDXF's note, and dimmed on the map. The server fetches the list and its footnotes every 3 hours and keeps the last good copy when ncdxf.org can't be reached; with no copy yet, every beacon shows as on the air. Listen still works on a beacon listed off, and the question still comes, because the list can lag by days (and misses beacons off for a contest), and hearing one back on is the report NCDXF asks for. Each beacon answer stores the list's status for that beacon when it arrived (`beaconStatus`, "OK" or "OFF"). The [Reverse Beacon Network](https://www.reversebeacon.net/) catches outages the list misses, such as a beacon switched off for a contest: after 01:00 UTC the first server that needs it downloads RBN's [file for the day before](https://data.reversebeacon.net/rbn_history/) (about 6 MB zipped), counts each beacon's `NCDXF B` spots, and saves the counts in the database for every server to read (`RbnBeaconDay`). A beacon with no spot all that day shows "Not spotted by RBN yesterday" in the strip, marked and dimmed like a beacon listed off, with Listen and the question still working. Only a whole day counts, since on ordinary days propagation alone can leave a beacon unspotted for 16 hours, and a day with under 2,000 beacon spots in all (RBN's own outage) marks nothing. No request waits on the download: until the day is saved the strip shows the day before, by date, or nothing. It runs a day behind, so a contest outage shows the day after. Each beacon answer also stores that day's spot count (`rbnSpots`, `rbnDay`). For the planned [#61](https://github.com/thehashrocket/skywave/issues/61) replay, the server also saves RBN's live [skimmer list](https://www.reversebeacon.net/nodes/) twice a day, from a Vercel cron (`apps/web/vercel.json`; it needs `CRON_SECRET` set in Production, or every run is refused). Each UTC day gets one row (`RbnSkimmerDay`) with every skimmer's callsign, grid, bands and last-seen time, plus the page itself gzipped so the day can be parsed again later. A list under 80% of the last saved day's (a page cut off partway), a page that ends partway through a row or has text after its last row, or one the parser can't read isn't saved as the day; such a page is kept instead (`RbnSkimmerRefusal`, up to 10 a day plus 2 refused by the 80% rule; a whole list whose save failed is always kept) so it can be parsed again later, and the day stays open for the next run. A real drop in RBN's list (after a contest weekend, say) is taken on its own once two days in a row agree within 10%, while the day before is still unsaved; until then, or if the parser itself needs a fix, the kept pages can be parsed again by hand into `RbnSkimmerDay`. A Production build without `CRON_SECRET` fails, so the cron can't be deployed unable to run. RBN keeps no history of where skimmers were, so a day both runs miss can't be recovered. With a beacon picked, "Did you hear it?" asks about that beacon only, once at least 7 seconds of its turn have played (counted from the first audio plus 1.5 s for the stream's delay); otherwise it waits for the beacon's next turn on that band, 3 minutes later. While the beacon strip is open and the drawer with it, the question (and the thanks after it) appears in the strip, right under that band's row, instead of under the status line. Until then that spot says what's happening: "{CALL} on air now" during its turn, "Listening for {CALL}: next on {freq} in m:ss" between turns, or, when the first turn after Listen didn't play long enough (a receiver usually takes longer than 1.5 s to start), "Missed the start; {CALL} is back in m:ss". When no question will follow the turn it shows, it adds "no question this time" (one question per 10 minutes in a tab and one per channel, or that turn won't have played long enough) or "questions are off in this tab" (after two ✕ closes; a new tab starts over). While the receiver is still connecting, with no audio yet, it says "Connecting…" instead, since whether a question will come isn't known until audio starts. The picked beacon stays marked in the strip as it moves up the bands, until you retune off its band or change receiver. Tuned to a beacon frequency by hand, it doesn't ask.
- **Strong signals now:** about 10 seconds after a receiver starts playing (and after Pick best's 15-second watch, if Pick best chose it), skywave scans that receiver's broadcast bands, medium wave plus the 14 shortwave bands on the dial, and lists the strongest signals it can hear right now, strongest first. Click one to tune it in AM, or in the mode of the station named on it when its schedule gives one (a numbers station in USB). The list ranks by how far a signal stands above the noise, so it can't tell talk from music; flat-topped signals such as digital broadcasts and noise jammers are left out and counted instead. The scan rides on the receiver's existing channel (no extra listener slot on the volunteer's Kiwi), takes a few seconds, and stops at 15 seconds (or when the receiver stalls) with the bands it finished. A complete scan is kept for 10 minutes per receiver, for everyone listening there; a partial one is shown but not kept, and a receiver that refuses the scan isn't asked again for a minute. **Scan again** makes a new scan, at most one every 30 seconds per listener (per IP address) on a receiver: sooner on the same connection, it shows the last answer; on a new connection, the scan waits out the rest of the 30 seconds. A receiver that sends no waterfall at all is reported as an error, not as an empty list. Ham bands aren't scanned.
- **Dial:** drag to tune coarsely (snaps to 5 kHz). Once the first audio of a visit arrives, the dial gets shorter so the waterfall has the room. ← and → tune 1 kHz from anywhere on the page (Shift for 10), so after clicking a saved frequency you can fine-tune without scrolling back up; they're left alone in text fields, the volume, the mode buttons and the map. With the dial focused, ↑ and ↓ step too, and Page Up/Down move 100 kHz (elsewhere those keys scroll the page). Saved frequencies sit right under the waterfall, above Find a station and Strong signals now. Crossing into a ham band switches to the conventional sideband automatically. On a touch screen, a finger tunes once it moves sideways (a scroll that starts on the dial doesn't), and a tap tunes where it lands; on a phone, a drag that ends near the edge of the visible dial scrolls the rest into reach.
- **Readout:** rest the pointer on the big number for half a second (or click it) and scroll to fine-tune, or focus it and use the up and down arrow keys; a scroll that just passes over it scrolls the page and never retunes. One AM channel per notch (10 kHz on medium wave with a receiver in the Americas, 9 elsewhere, 5 on shortwave), 100 Hz in SSB, 10 Hz in CW; hold Shift for ten. Or click it and type an exact frequency, in kHz or with a unit (`7.2 MHz`, `7200k`). Anything else stays in the box, flagged, with the range to use; Escape puts the current frequency back. skywave remembers the last frequency and mode, a pinned receiver, and the last receiver you heard (for Back), for your next visit.
- **Find a station:** above Strong signals now. With nothing typed it lists every broadcast the schedule has on the air now (the same one Station names reads: EiBi, Priyom's numbers-station slots and the signal stations catalog), the shortwave broadcast bands first (lowest frequency up) and then everything else under "Outside the broadcast bands". Type part of a station's name (a catalog station's other names count too) to see its broadcasts from that schedule that are on the air now, then the ones starting in the next 24 hours (UTC, with how long until each), one row per frequency, time and language (with one language picked, a row in just that language leaves it off, since the filter already says it). Accents, case and word order don't matter, and EiBi's short forms are spelled out ("radio triunfal" finds "R.Triunfal Evangélica", "voice of america" finds "VoA"). A row says where the broadcast is aimed ("to South Asia"; the names come from EiBi's README, bundled with the snapshot) and, when the playing receiver's finished band scan heard a strong signal on that frequency, "Strong here". Click a row to tune there: in the mode Priyom or the catalog gives for its own rows (a Priyom RTTY slot shows Priyom's listed frequency, then its dial 2.125 kHz lower in USB: "17,532 RTTY · dial 17,529.875 USB"); otherwise AM, except CW for EiBi's Morse listings (language `-CW`) in any band, USB in the HF aeronautical and maritime mobile bands (Volmet, coast stations), and the dial's own choice in a ham band; a short named list of AM broadcasters EiBi lists inside those mobile and ham bands (Sound of Hope, CNR1 Firedrake, Voice of Korea, Rádio Tury, Star-Star, Presidential Pirate) still tunes AM. Clicking with nothing playing, or on a frequency the receiver doesn't reach, offers Pick best for the clicked row's frequency and mode, even if the dial has moved since (pick source `search` for a row found by name, `browse` for one from the on-now list). Both lists narrow by **Aimed at** (Any, a broad region such as North America or Europe, or one of the area and country codes the schedule uses; a code aimed at two regions, like "the Americas" or Russia, counts for both) and **Languages** (a filterable checklist of the schedule's languages; typing in its filter lists names that start with what you typed first, so "hin" puts Hindi above Chinese; a broadcast in "French, English" counts for English, one with no language only shows under Any), with **Include non-voice** for time signals, Morse and data, on by default. The filters are remembered in the browser; a saved language the new season doesn't use stays picked and is marked "none in this schedule". While a receiver with a known position plays, a link offers its region ("Aimed at North America (where this receiver is)?"); it's never applied without the click. When the filters hide everything, the line says so ("BBC has 3 broadcasts in the next 24 hours, none in Spanish to Asia.") with a Clear filters button. Results come 20 at a time (8 first on a phone). It's a schedule, like Station names: a listed broadcast may be off the air or out of reach.
- **Station names:** who's scheduled on the air now, from the free [EiBi](http://www.eibispace.de/) shortwave schedule: under the readout for the tuned frequency, on each Strong signals row ("KBS World Radio · English"), and as marks across the top of the receiver's waterfall, named where they fit (nearest the tuned frequency first). A shared frequency says "+2 more": under the readout, press it for the others; in the list, hover a name or tune the row. It's a schedule, not a log: a listed station may be off the air or not reach the receiver, and an unlisted one may be on. Listings within half a kHz count, by UTC time and day. The readout, the waterfall marks, Strong signals, Find a station and a signal station's "Did you hear it?" all read one schedule (#148, `src/lib/on-air.ts`): EiBi's, with numbers stations named only where [Priyom](https://priyom.org/)'s schedule has them (EiBi's season grid for them is dropped), and time signals and markers under the signal stations catalog's names on the catalog's frequencies. The Pip and The Squeaky Wheel switch channels at EiBi's hours for the current stretch of months, and the Signal stations panel and their own pages follow the same hours (#168), so all three name one frequency. On a shared frequency the readout, the waterfall and Strong signals name first a station aimed where the receiver playing is (with nothing playing, the region Find a station is filtered to); with no region to decide, a signal station, or a numbers station in a slot Priyom confirms, comes before EiBi's listings (#152), so 10,000 kHz reads "WWV · Time signal +4 more". The EiBi question reads EiBi's own rows instead, so where it's asked it can name a station other than the one the readout names. On 10 MHz, where WWV and WWVH are both on the air, a hand-tuned listener is instead asked which time station they heard (#150). While Priyom's schedule can't be had, EiBi's rows for those numbers stations come back marked "season schedule, not confirmed" ("(unconfirmed)" on the waterfall), and nothing is asked about them. "On now" everywhere goes by the server-corrected clock, like the UTC clock, and so does the map's greyline. When a fetched EiBi file lists a "… Numbers" station no catalog entry names, the server logs a warning: add the name to the matching catalog station's `eibi` list in `src/lib/signal-stations.ts`, or its season grid shows as plain EiBi rows. The web server fetches the season's file once a day; if eibispace.de can't be reached, it uses a copy bundled with the app (the `Refresh EiBi snapshot` workflow updates it after each season change, on 1 April and 1 November, and opens a PR; `pnpm --filter web eibi:snapshot` does the same by hand). The server also reads where each broadcast is sent from: the schedule's site code, looked up in the transmitter-site table in EiBi's [README](http://www.eibispace.de/dx/README.TXT) (`src/lib/eibi-sites.ts`). The page never gets the sites; they're only saved with "Did you hear it?" answers (see **Going public**). The server starts from the table bundled in the same snapshot and, when an answer is saved, refreshes it in the background at most once a day (ten minutes after a failure), keeping the last good table if the README can't be fetched or has under 80% of the sites in the largest table it has accepted. The snapshot workflow bundles the table too, and the README's country and target-area names that Find a station shows (a target code EiBi doesn't name is listed in its PR body); if the README fails or is refused there, it keeps the bundled sites, shows a warning on the run, and says so in its PR. The PR also gives the bundled table's site count and the new one ("1,698 → 1,690"), so a list that shrinks season by season shows up in review. If that refusal repeats season after season, EiBi may have really dropped more than a fifth of its sites. A redeploy won't help, because the server and the workflow both compare against the bundled table. To take the smaller list, work locally. Delete the `sites` key from `apps/web/src/server/eibi-snapshot.json`, run `pnpm --filter web eibi:snapshot`, and commit the file only if the script saved new sites. If the run fails, put the file back with `git checkout apps/web/src/server/eibi-snapshot.json`. With no bundled sites, it takes the README as a first parse (at least 1,000 sites). Never commit the file without its `sites` key, because the server can't start its site table from it and every answer would be saved without its transmitter sites.
- **Waterfall:** right under the status line. Until the first audio of a visit it's a short strip ("A blank receiver picks the best one."). Then a row of widths appears above it:
  - **Audio** shows the ±6 kHz the Kiwi is sending for your audio.
  - **15 kHz**, **60 kHz** (the default) and **230 kHz** show the receiver's own waterfall around the dial, with the frequencies along the bottom. It stays put while you tune inside it and moves when you get near an edge.
  - **Band** (named for the band, say "31m band") shows the whole band the dial is in. It's available only inside a band; leave the band and the waterfall goes back to 60 kHz.

  Click a signal to tune to it; on the wider views the click lands on the nearest channel (the same steps as the readout's wheel). The line along the top is the spectrum right now (a station is a spike there before it has drawn much below), steadied a little from frame to frame. The shaded strip is your current mode's passband, darker where it crosses that line, and the dashed line with the red pointer is the tuned frequency. The receiver's waterfall rides on the same channel as your audio, so it takes no extra listener slot. Like the band scan, it's asked for only once a receiver has played for 10 seconds and Pick best is done with it, so receivers you pass through aren't bothered; until then the audio view shows and the row says the receiver's waterfall starts in a few seconds. While the band scan runs, that waterfall holds still and says so; it carries on when the scan is done. A receiver that refuses its waterfall says why in the picture; pick **Audio**, which always works.
- **Audio spectrum:** once audio has played, a small spectrum of what's coming out of the speaker sits under the S-meter and volume, from 0 Hz to the top of the audio (about 6 kHz). It shows the shape the mode's passband lets through and that the audio is alive while a station pauses. The volume doesn't change it.
- **Modes:** AM for broadcasters and WWV. LSB below 10 MHz and USB above for ham voice. CW for Morse; the service tunes 700 Hz low so code comes out as a 700 Hz tone. From anywhere outside a text field, **A**, **U**, **L** and **C** pick AM, USB, LSB and CW (not with Shift, Ctrl, Alt or ⌘); **Letter keys change mode** under the mode buttons turns them off, and the choice is remembered. Clicking a mode with the mouse leaves ← → tuning rather than switching modes.
- **Tuning bar:** scroll down past the tuning controls and a bar pins to the top of the window with the frequency, the modes, the receiver and Listen/Stop, plus the UTC time ("14:05 UTC") on screens wider than 860px. Press the receiver to jump back up to the receiver drawer.
- **UTC clock:** next to the wordmark, the UTC weekday and date sit over a 24-hour clock that ticks each second ("Mon 23 Nov" over "14:05:09 UTC"). It runs on the server's time, like the beacon schedule, so it agrees with the beacon slots and GhostNet countdowns even when your device's clock is off. On a narrow screen it wraps under the wordmark.
- **Saved frequencies:** on a public site each browser keeps its own list (up to 200; a full list refuses the next save and says so, keeping the name you typed), with the shared presets under "Worth a listen". A station you save shows when, in UTC: "saved Sat 2214 UTC" within 6 UTC days, then the date ("saved 8 Nov 2214 UTC"), with the year once it's from another year. Hover for the full date and your local time. Stations saved before 0.48 and the shared presets show no time.
- **Etiquette:** each listener takes one of a volunteer's 4–8 channels. The service caps itself at `MAX_SESSIONS` listeners in all, `MAX_SESSIONS_PER_RECEIVER` (default 1) on any one Kiwi so a crowd can't fill a volunteer's receiver, and `MAX_SESSIONS_PER_IP` (default 2, counted like `MAX_SOCKETS_PER_IP` below) for one address so a few tabs can't hold every slot; both are whole numbers of at least 1, or the service stops at startup. A receiver that already has its `MAX_SESSIONS_PER_RECEIVER` Skywave listeners is refused with code `skywave_cap` (`busy` for a page built before that code), so Pick best moves on without spending a try; a switch onto one from a page that knows that code is refused before anything stops, so the current receiver plays on; at `MAX_SESSIONS` the service is full and refuses with code `skywave_full` (uncoded for a page built before that code), which ends Pick best like a service failure and is written to the receiver log either way, so `deploy/stats.sh` counts the refused tunes (#146; logged as host `<many>`, since the refusal is about Skywave rather than the receiver, one line per connection every 10 s with the repeats carried as `suppressed=N`); the per-address limit is uncoded. Receivers whose owners ask not to be used go in `BLOCKED_RECEIVERS` (comma-separated `host` or `host:port`, `[v6]:port` for IPv6; a bare host covers every port): the service refuses them with code `blocked`, and the same variable on the web app hides them from the list and map. Each Kiwi lists the service in its user list as `KIWI_IDENT` (`skywavehf.com` in production), or as "skywave" and the listener's name for a listener who set one (see Your name on receivers), which leads owners to the site's `/owners` page: what skywave does on their receiver, these limits, and how to opt out (the repo's opt-out issue form, or setting their Kiwi's `ext_api` to 0). The service drops a session after `MAX_SESSION_MINUTES` (at least 1, or `inf` for no limit; any other value stops the service at startup). A browser socket with nothing playing and no messages for `IDLE_SOCKET_MINUTES` (default 10, same rules) is closed; the page opens a new one on its next tune. One public address can hold at most `MAX_SOCKETS_PER_IP` sockets (default 8, one per tab; IPv6 counts by /64; a whole number of at least 1, or the service stops at startup). Everyone behind a shared address (carrier NAT, a campus or office) shares that number, so raise it if many of your listeners do. Private and unknown addresses aren't counted, so behind a reverse proxy that reaches the service from a private address the limit applies only once `FORWARDED_ALLOW_IPS` lets the service see real users; a proxy on a public address would count as one user, so set it there too (see Deploying). The service pings each socket every 20 seconds, which keeps proxies that count those pings (nginx's `proxy_read_timeout`) from cutting idle sockets; a load balancer with a shorter idle limit, or one that ignores pings, cuts them first and the page reports a lost connection instead of a quiet hang-up.

## Learning the DSP offline

You don't need the browser to experiment. These scripts use the exact same `Demodulator` the live service does:

```bash
cd apps/radio
.venv/bin/python scripts/make_test_signal.py --out synthetic.wav      # known signals, no receiver needed
.venv/bin/python scripts/record_iq.py --host <kiwi> --freq 10000 --seconds 30 --out wwv.wav
.venv/bin/python scripts/plot_spectrum.py wwv.wav                     # spectrum + waterfall
.venv/bin/python scripts/demod_wav.py wwv.wav --mode am               # writes wwv-am.wav to play
```

The loop is: edit `skywave_radio/dsp.py`, rerun `demod_wav.py`, listen. Good first experiments: swap the AM envelope detector for a synchronous detector (less fading distortion), make the AGC hang time adjustable, add a noise blanker, or add NFM for 10 meters.

Browser ↔ service protocol: the browser sends JSON (`{"type":"tune","host","port","freqKhz","mode","source?","secure?","codes?"}`, `{"type":"stop"}` or `{"type":"scan","id","fresh?"}`; `"retune":true` marks a dial move, which the service applies only to the session playing that receiver: with nothing playing it does nothing, and with another receiver playing it answers with that one's status, so a dial move that crosses a session's ending never opens a Kiwi channel; `"source":"list"` marks a receiver from the public list, which the service only dials on public addresses even with `ALLOW_PRIVATE_HOSTS` on, and `"secure":true` dials an https-only receiver over `wss://`, with its certificate checked against the hostname. A plain receiver that redirects to https on the same hostname, on port 443 or its own port, is followed once; any other redirect is refused as `unreachable`). The service sends JSON status messages (`{"type":"status","state","message?","code?","retryAfterMs?","host?","port?","sampleRate?","mode","freqKhz","features"}`; `features` lists `"scan"`, and the browser only sends `scan` to a service that does), scan replies (`{"type":"scan","id","host?","port?","state":"scanning|done|error",...}`; `done` adds `signals` [`{"freqKhz","snrDb","band"}`], `hidden`, `bandsDone`, `bandsTotal`, `partial` and `atMs`, `error` adds `message`; the browser applies only the reply for its newest request and current receiver, and a scan failure never comes as a status) and S-meter messages, plus binary frames: first byte `0x03` for mono int16 audio at the Kiwi's sample rate (full scale 32767), `0x04` for a 512-bin spectrum row (a float32 base level in dB, then one uint8 per bin at base + v × 0.5 dB). A service from before that switch sends `0x01`/`0x02` (Float32 audio and dB) instead; the browser reads both, so for that change deploy the web app first. A tune's `codes` lists error codes the page knows that an older page wouldn't (today `["skywave_cap","skywave_full"]`); the service sends such a code only to a page that lists it and the older equivalent (`busy` for `skywave_cap`, no code for `skywave_full`) to the rest, so a tab left open never reads a new code as the service's own failure. To such a page, a switch onto a receiver at Skywave's own cap while another one plays is answered with `{"type":"refused","host","port","code","message","stillOn":{"host","port"}}` and then the session's own status for the receiver in `stillOn`, which keeps playing; the page keeps the refusal apart from statuses (an error status followed at once by a listening one would be merged into one render and lost), points its dial back at `stillOn`, and Pick best moves on (or, when the refused receiver is the one a run was going back to, ends the run with "Couldn't get back to …"; Pick best matches hosts in `refused` messages and statuses without regard to case). An older page gets the old order: the current receiver stops, then a `busy` error. An error status carries a `code`: `busy`, `skywave_cap` (Skywave's own per-receiver limit), `skywave_full` (Skywave's own overall limit, `MAX_SESSIONS`; the one code not about the receiver, so Pick best stops on it as on an uncoded error), `no_apps` (the receiver only takes listeners on its own web page: `ext_api=0` in the public list, which the web app hides), `down`, `unreachable`, `timeout`, `password`, `redirect`, `bad_rate` or `closed` from the Kiwi connection, and `invalid`, `dns` or `blocked` when the address is refused (`invalid` also covers an address the Kiwi client can't build a URL for). For the `source`/`code` change, deploy the radio service before the web app: the browser relies on both, and an older service ignores `source` and sends errors without a `code`. Pick best moves to the next receiver on any other coded error (they're all about that receiver), stops on an uncoded one or `skywave_full` (a bad request, the service's own listener limit (uncoded from a service older than `skywave_full`) or DNS lookup capacity, an internal error, or a dropped connection), and uses `host`/`port` to ignore statuses from earlier attempts. A tune's `port` is a whole number from 1 to 65535 (null, absent or the number 0 mean 8073; text like `"8073"` is read as a number); anything else, such as `true`, `""`, `"0"` or `8073.9`, is a bad request. A bad request while a session still holds its receiver leaves that session playing: the uncoded error is followed by the session's own status again (`listening` or `connecting`, with its `freqKhz` and `mode`); with nothing playing, the error is the whole answer. The one uncoded error with `retryAfterMs` (this client's earlier address lookup is still stuck) gets the same receiver tried once more after that wait. A web build ignores codes it doesn't know, treating those errors as uncoded. The service closes a socket left idle for `IDLE_SOCKET_MINUTES` with WebSocket close code `4000`, which the page treats as a quiet hang-up (a Listen still in flight when it closes goes out again on a new socket), and refuses a socket past `MAX_SOCKETS_PER_IP` with `4001`, which the page explains. An older web app reports either one as a lost connection, so for that change deploy the web app first.

The web app's design system (colors, fonts, spacing, components, and where the code is inconsistent) is recorded in [DESIGN.md](DESIGN.md); the receiver map's design record is [docs/designs/receiver-map.md](docs/designs/receiver-map.md).

## Deploying the radio service

The ready-made setup is a small DigitalOcean Droplet running `docker-compose.prod.yml` (the service behind Caddy, which handles TLS), deployed by GitHub Actions on every push to `main`; see [deploy/README.md](deploy/README.md). On any other box, the dev compose file works too (`docker compose --profile radio up -d radio`). Five things matter either way (the prod compose file already covers 1, 3 and 5):

1. **TLS.** A web app served over `https` can only open `wss://` sockets, so put the service behind your usual reverse proxy (Caddy, nginx) and set `NEXT_PUBLIC_RADIO_WS_URL=wss://radio.example.com/ws`. This is also why the service exists at all: most Kiwis only speak plain `ws://`, which browsers block from secure pages.
2. **Lock it down.** Set `ALLOWED_ORIGINS` to your web app's origin. Any script can fake an Origin header, so the service refuses to start without `RADIO_TOKEN` once any non-localhost origin is allowed. The token ships to the browser in the web app's JavaScript, so set `APP_PASSWORD` on the web app (see below) to keep the token behind a password. `ALLOW_PRIVATE_HOSTS` stays off so the service can't be pointed at your internal network or tailnet.
3. **Trust your proxy, and only it.** The service lets each user have one address lookup running at a time, keyed by their IP. Behind a reverse proxy it only sees the user's IP if it trusts that proxy's `X-Forwarded-For` header, so set `FORWARDED_ALLOW_IPS` to the proxy's address as the container sees it (with docker compose and a proxy on the host, the bridge gateway, often `172.17.0.1`). Never use `*` while port 8765 is reachable without going through the proxy: anyone could then claim any IP. docker-compose publishes 8765 on every interface, and Docker's own port forwarding can make direct connections arrive from that same gateway address, so with a proxy on the host change the mapping to `127.0.0.1:8765:8765`; then only the proxy can reach the service and the gateway address really means the proxy. Until it's set, the limit falls back to one lookup per connection, which still works but lets one user open more connections to get more lookups, and `MAX_SOCKETS_PER_IP` doesn't apply while the proxy's address is private (a public one would count as a single user).
4. **One process.** Run the service as a single process: one uvicorn worker, as the Dockerfile does, and one copy per outgoing IP address. The band scan pairs its waterfall with a listener's audio by the timestamp in the Kiwi URL, and that timestamp is unique only within one process (`KiwiConnection._last_timestamp` in `kiwi.py`). With several workers, or several copies behind one outgoing address, two listeners could get the same timestamp, and one listener's scan could end another listener's audio.
5. **Let it stop cleanly.** On a stop, uvicorn closes every listener's socket at once (listeners see the connection drop and press Listen again once the service is back) and gives their teardowns, mostly closing each volunteer's Kiwi, up to 15 s (`--timeout-graceful-shutdown 15` in the Dockerfile). It then cancels any still running, and the service waits up to 10 s more, in total, for those Kiwi connections to close (a cancelled listener's teardown takes at most about 9 s), and gives any still running about 9 s more as it exits. That last step has no cap of its own: a scan task that ignores its cancels holds the exit until docker kills the container. docker-compose gives the container 40 s (`stop_grace_period`) before killing it; if you run the image another way, give it at least that long, or volunteers' receivers see an abrupt disconnect on every restart.

**Deploy order.** For the switch to int16/uint8 binary frames (`0x03`/`0x04`), deploy the web app before the radio service: the new web app still reads the old frames, but an older one plays nothing from the new ones. For the `no_apps` error code, deploy the web app first too, so the receiver list stops offering those receivers before the service starts naming the refusal. Such a receiver usually plays for about 10 s before it refuses; Pick best keeps watching for 15 s after audio starts, so it still moves past one. The band scan needs no order: the radio service lists `"features": ["scan"]` on its statuses and the web app only asks a service that does, so either side can go first or be rolled back. The protocol notes above say which side goes first for each protocol change.

## Deploying the web app

If the web app is reachable from the internet, set `APP_PASSWORD`. Every request then needs that password via HTTP Basic auth (any username): pages, the preset API, and the static JavaScript that contains `NEXT_PUBLIC_RADIO_TOKEN`. Two paths skip it: `/api/cron/`, which Vercel's cron calls with `CRON_SECRET` instead, and `/api/signals/freshness`, which the weekly GitHub Action calls with `SIGNAL_FRESHNESS_SECRET`. So the daily skimmer snapshots and the weekly freshness report keep running on a locked site. Leave it empty for local development. `src/proxy.ts` does the check.

### On Vercel

Only the web app runs on Vercel. The radio service holds one long-lived process and listener sockets for up to an hour, which Vercel Functions don't, so it stays on your own box (see Deploying the radio service).

1. **Project.** Import the repo with the root directory set to `apps/web` (Next.js preset). Add `ENABLE_EXPERIMENTAL_COREPACK=1` for Production and Preview so the build uses the pnpm version pinned in the root `package.json`. Node comes from `engines` in `apps/web/package.json` (24.x), not `.nvmrc`. Leave the Build Command at its default: Vercel then runs `vercel-build`, and an override skips the migrations.
2. **Database.** Install Neon from the Vercel Marketplace on the project, in the same region as your Functions (`iad1` unless you changed it). It sets `DATABASE_URL` (pooled) and `DATABASE_URL_UNPOOLED` for Production and Preview. Check that the integration creates a database branch per preview: previews run migrations too, and without branching they run them against production. The build runs `vercel-build`, which generates the Prisma client (`prisma generate`: a cached install skips `postinstall`, and the client isn't in git), then applies migrations (`prisma migrate deploy`, over the unpooled URL), then runs `next build`; a failed migration fails the deploy and the previous one keeps serving. So keep each migration compatible with the code that's already live. After the first production deploy, seed the starter presets once: `DATABASE_URL=<production unpooled URL> pnpm db:seed`.
3. **Environment.** Set `APP_PASSWORD` for Production and Preview (but see **Going public** below). Set `NEXT_PUBLIC_RADIO_WS_URL=wss://radio.example.com/ws` and `NEXT_PUBLIC_RADIO_TOKEN` (the radio service's `RADIO_TOKEN`) for Production only: previews can't play audio anyway (step 5), and leaving the token out keeps it out of every preview bundle. A Vercel build with the token set and `APP_PASSWORD` empty fails (`next.config.ts`), since the token would then ship in public JavaScript. The `NEXT_PUBLIC_` values are baked in at build time: redeploy after changing them. For the first production deploy, use a throwaway token; put the real one in only after step 4 passes. Also set `CRON_SECRET` (a long random string, such as `openssl rand -hex 32`) for Production: Vercel's cron (`apps/web/vercel.json`) sends it to `/api/cron/rbn-skimmers` twice a day to save RBN's skimmer list, and a Production build without it fails (`next.config.ts`). Set `SIGNAL_FRESHNESS_SECRET` (another long random string) for Production too, and the same value as the `SIGNAL_FRESHNESS_SECRET` Actions secret (the workflow runs in the `production` environment): the Signal freshness workflow (`.github/workflows/signal-freshness.yml`) sends it every Monday to `/api/signals/freshness` and keeps one open issue labelled `signal-stations` and `freshness`. Without it the route refuses every call and the workflow fails; the build doesn't check it. The workflow reads `https://www.skywavehf.com` unless the Actions variable `SITE_URL` names another site.
4. **Check the password covers the JavaScript before the radio service trusts the site.** On the production hostname (the project's domain, such as `skywave-xxxx.vercel.app`, not a guess at `<project>.vercel.app`, which may be someone else's), open a `/_next/static/…` file in a private window: it must ask for the password, and the 401 must carry `WWW-Authenticate: Basic realm="skywave"`. Check on production because Vercel's own protection sits in front of previews and answers 401 there without that realm. Only then put the real token in, redeploy, and add the production origin to the radio service's `ALLOWED_ORIGINS` (comma-separated, exact scheme and host, no trailing slash); list every production hostname, custom domains and `www.` included. If a file loads without the password, the token is public: stop, fix it, and rotate `RADIO_TOKEN` (and the web app's copy) before going on.
5. **Previews can't play audio.** `ALLOWED_ORIGINS` lists only the production origin and every preview gets a new one, so the radio service refuses previews and Listen reports it unreachable. Previews still show the dial, map, receiver list and presets.

### Going public

To open the site to everyone, remove `APP_PASSWORD` from Production (keep it on Preview) and set `NEXT_PUBLIC_SITE_PUBLIC=1` for Production, then redeploy. The build allows the token without a password only with that flag. The token is then public, so the radio service's own limits are what protect it and the volunteers' receivers: `MAX_SESSIONS`, `MAX_SESSIONS_PER_RECEIVER` and `MAX_SESSIONS_PER_IP`, plus `ALLOWED_ORIGINS`, which stops other sites' pages but not scripts. In public mode the shared presets are read-only suggestions (the API refuses creates and deletes), and each browser keeps its own saved frequencies in localStorage. Links of the form `/?f=9580&m=am&rx=host:port` (`&tls=1` for an https-only receiver) open the page tuned there; Copy link makes one. `&sig=<slug>` names a signal station (#100): the page tunes it if it's on the air, scrolls to the Signal stations panel, and Listen ranks receivers by the station's path. A numbers station's frequencies come from Priyom's schedule, so its link needs `f=` (and usually `m=`) to tune it; with `sig` alone the page only brings the panel into view. A signal station gets "Did you hear it?" (#101) after a Listen on it (a panel row's, or header Listen on a station a link named, which first checks the station is on the air on the dial's frequency), or, since #148, with the dial on a frequency where it's the only station on the air, however the dial got there (several stations on one frequency keep the EiBi question, unless two or three of them are catalog stations: then, since #150, one question asks which was heard, "Heard WWV (a man's voice)", "Heard WWVH (a woman's voice)", both, nothing, "Something else / can't tell" or didn't open, sent to `reports.submitGroup`, which files one signal row per station sharing an `askGroup` id, "Heard WWV" filing WWVH as not heard, "can't tell" filing nothing, and counts the group as one of the listener's answers but each of its rows against the receiver's 30 an hour; neither the weekly freshness report's "possibly off the air" nor the "last heard" counts treat a station not heard beside one that was as not heard), and then it's the only thing asked about there: once a minute of audio has played, counted as for a beacon from the first audio plus 1.5 s, all of it before the station goes off (always-on stations never do; a numbers station's Priyom transmission counts as on for 10 minutes from its start). One that goes off first isn't asked about. WWV and WWVH share 2.5, 5, 10 and 15 MHz, so their questions add the voice that tells them apart ("Did you hear WWV (a man's voice) …?"); the answer is stored under the station alone. Turn on Web Analytics in the Vercel project for the `<Analytics />` in the layout to record anything. Reception reports ("Did you hear it?", stored as `ReceptionReport`) are anonymous writes. When Pick best chose the receiver, a report also keeps how it chose (issue #61): when, which button started the run, the receiver's place in the ranked list, the top 10 receivers' `host:port`, and its listed position, SNR and user count, plus `pickVersion`, the version of the page's rules that recorded it (none when the page sent no version: answers saved before version 2, and answers sent later from tabs opened before that deploy, which the server still checks like any other; the server takes versions 2 to 11, so a tab opened before a later version's deploy still stores the one it sent; version 4 is the page's server clock counting from its monotonic clock and measured again after the computer's clock jumps, version 5 drops the context of a pick made during such a jump if the time then moves before it's measured again, and version 6 measures to the millisecond on a schedule and drops a held pick's context on any correction of the clock, so a version 6 pick time is good to the measurement's error (typically well under half a second), and to 1.5 s at worst on an ordinary visit; version 7 keeps those rules and adds runs started from station search's Pick best button (source `search`), version 8 adds runs started from a GhostNet row's Listen (source `ghostnet`, ranked by the net's region), version 9 adds runs started from Find a station's on-now list (source `browse`, while `search` stays for a typed name), and version 10 adds runs started from a signal station's Listen (source `signal`, ranked by the path from its transmitter), and version 11 tries receivers another Skywave listener already has after the others (#155), so the order a run walks can differ from the ranked list whose place it stores (the context doesn't say which were held); #61 queries should group versions 6 to 11 as one rule set. The page sends the version and the server can't check it: a row's `createdAt` against the deploy times posted on #61 says which server rules took it), and `candidatesListed`, how many of the top 10 were on the server's list when the answer arrived (fewer than all: a made-up key, or a receiver that left the list since the pick; the context is kept either way). These describe public receivers from the public list, not the listener; a hand-picked receiver stores none, and neither does a Pick best choice once the listener has moved the dial off the frequency it ranked for or chosen a receiver by hand (the one playing included), even after coming back, nor a receiver a run was still tuning when it was stopped or ended on a service error. An answer keeps its question's context only if no choice was dropped after the question appeared, so it also stores none when a run moved to another receiver, or the dial moved away and back, before a later run picked the same receiver again; a beacon Listen before the receiver list has loaded drops any earlier choice too. The server drops context that is malformed (each candidate must be spelled exactly as the page writes it, so one receiver can't appear twice) or doesn't fit the report (another frequency, another receiver at that rank, a button that can't lead to that question (beacon Listen for a broadcast or a signal station, anything else for a beacon), made more than 5 s in the future or over 3 hours ago, or too late in a beacon's slot to have led to hearing it), logs a warning, and keeps the answer. An answer about an EiBi broadcast also stores `txSites` (issue #72): every transmitter site the station or stations asked about were listed from on that frequency, at the latest minute of the last 5 minutes each was on the air, from the server's cached schedule and site table. Each is its EiBi site key with its coordinates (none when EiBi lists none; several, up to 20, for a group of transmitters), or `{key: null, country}` when EiBi doesn't say which site. It describes the broadcaster, not the listener; beacon answers store none, and if the lookup fails the server logs it and keeps the answer without sites. The server keeps one only about a receiver on its cached public list and a station its cached EiBi schedule had on that frequency in the last 5 minutes, never an EiBi answer naming a numbers station Priyom's schedule drives, which the page asks about as a signal station since #148 (older EiBi answers about those stations are left out of #61's analysis by the CTE in `apps/web/analysis/61-exclude-priyom-eibi.sql`;
